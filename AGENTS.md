# Arbeitsregeln für diese Webseite

1. Zuerst `docs/WORK_STATUS.md`, offene Issues und den tatsächlichen Stand von `main` lesen. GitHub Pages veröffentlicht `main`, nicht einen alten Designzweig.
2. Parallel laufende Projekte auf dem GEEKOM-PC weder wechseln noch zurücksetzen, beenden oder mit globalen Installationen verändern. Einen eigenen Website-Arbeitsordner verwenden.
3. Bestehende Originalbilder und bestätigte Firmen-/Kontaktdaten erhalten. Keine KI-Referenzen, erfundenen Kundenbewertungen, Garantien oder unbelegten Leistungsversprechen.
4. Bei Formulararbeiten Versand und reine Nachrichtenvorbereitung unterscheiden. Kein externer Versanddienst ohne geklärte Freigabe, Datenschutzgrundlage, Empfängeraktivierung und echten Zustelltest. Keine Zugangsdaten in dieses öffentliche Repository schreiben.
5. Statische Tests UND echten Browser-Audit ausführen. Fehlerfälle, Touch-Bedienung und Darstellung prüfen; PASS nicht allein aus Quelltextsuche ableiten. Simulierte API-Antworten als solche dokumentieren.
6. Vor Merge erneut auf parallele Änderungen prüfen. Nicht force-pushen. Nur mit der im Auftrag erteilten Freigabe veröffentlichen.
7. Jeden abgeschlossenen Arbeitsschritt in `docs/WORK_STATUS.md` und dem Pull Request nachvollziehbar dokumentieren. Verbleibende Aufgaben als Issues mit Akzeptanzkriterien festhalten; keine allein im Chat gespeicherten Zusagen.

8. Vor dem Merge alle PR-Reviews und Kommentare lesen. Berechtigte Befunde beheben und erneut prüfen; ein grüner CI-Lauf ersetzt keine Prüfung der Review-Hinweise.
